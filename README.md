# PS-13 · The Two-Minute Morning Brief

Daily MIS reports for the state government are compiled by hand from three
separate transport systems — Metro, BRTS and AMTS. It takes hours, and the
exceptions that matter (a station down 20%, a gate outage plus rain) get buried.

This prototype turns the raw daily feeds into a **one-page brief with the
exceptions already flagged and their likely causes named.** It runs entirely
offline (no pip install, no internet, no cloud model).

---

## Where the data comes from  (read this first)

There is **no live feed** from the operators and **no dataset shipped with the
brief**. So the prototype works two ways:

1. **A synthetic sample feed**, generated by `data_gen.py`, written to `data/`
   as four CSVs. This is what ships in the box so the demo runs immediately.
2. **Your own CSVs** in the same folder/schema — drop them into `data/` and the
   brief is computed from them. This is the path to a real pilot.

So the chain is: `data/*.csv` → `engine.py` (baseline + flags + causes) →
`server.py` (the web report). No numbers are downloaded; every figure on the
page is derived from the four CSVs on disk.

### The four feeds (schema)

| file | columns | meaning |
|---|---|---|
| `ridership.csv` | `date,system,unit,riders` | daily riders per station/stop/route |
| `weather.csv` | `date,rain_mm,temp_c` | city-wide weather for that day |
| `outages.csv` | `date,system,unit,asset,hours` | asset faults (gate, lift, escalator…) |
| `events.csv` | `date,system,unit,note` | events/diversions; blank `unit` = whole system |

`system` is one of `Metro`, `BRTS`, `AMTS`; `unit` is a station, a BRTS stop or
an AMTS route.

## Run it

### 1. The web report (main entry point)

```bash
python data_gen.py            # writes the sample CSVs into data/   (once)
python server.py              # -> http://127.0.0.1:8888/
```

Then open http://127.0.0.1:8888/ . Add `--refresh 30` to auto-reload every 30 s,
`--port 9000` to change the port, `--open` to launch a browser.

> Note: on some Windows hosts ports 8000/8080 are in the reserved range and will
> refuse to bind (`WinError 10013`). The default here is **8888**; use `--port`
> to pick another free port.

Routes served:

| path | what |
|---|---|
| `/` | the dashboard (the report) |
| `/api/brief.json` | the analysed facts as JSON |
| `/brief.md` | the plain-text one-pager |
| `/health` | `ok` + latest date |
| `/data/<name>.csv` | the raw input feed |

The page is **fully self-contained** — styles and charts are drawn server-side
as inline SVG, with no CDN or external requests, so it keeps working when the
network drops.

### 2. Plain CLI (no server, no deps)

```bash
python brief.py                          # writes brief.html (open / Ctrl+P to PDF)
python brief.py --save-sample data       # export editable CSVs
python brief.py --data-dir data          # run on your own CSVs
```

### 3. Full version with a local AI summary (optional)

`v1/` has a pandas build plus an optional local-Ollama summary and a Streamlit UI.
It falls back to a template summary automatically if the model isn't running.

```bash
cd v1
../venv/Scripts/python.exe morning_brief.py            # Markdown brief
../venv/Scripts/python.exe morning_brief.py --llm gemma3
../venv/Scripts/streamlit.exe run app.py               # web UI
```

## How the brief is computed

- **usual** = mean of the *same weekday* over the last 4 weeks (falls back to the
  last 7 days for a unit with little history). Using the same weekday stops
  weekends from looking like anomalies.
- **flag** a unit when `|change| >= 10%` **and** `z >= 2` (z uses stdev floored at
  2% of usual, so a steady unit can't trigger on rounding).
- **causes** are rule-matched, never invented:
  - an **outage** or **event** for that unit today → status **likely**;
  - **weather** (rain ≥10 mm, heat ≥44 °C) → status **possible**, and only when the
    drop sits near the system-wide dip, so an unrelated fall isn't blamed on rain;
  - nothing matches → status **UNEXPLAINED**, surfaced for a human to check.
- Every cause shown on the page can be traced to a row in the feeds — the
  "Signals used to explain the day" panel lists them.

## Assumptions (state these in the demo)

The bundled data is **synthetic**, produced by `data_gen.py`, and is meant only
to exercise the logic: 60 days of history, 37 units, weekend ridership at 70% of
weekday, ~3% daily noise, a real rain day, two asset outages, three events and
eight planted rider movements so the demo shows one clean case of each status
(**likely / possible / unexplained**). Reruns are deterministic (fixed seed).
Thresholds (10% / z 2) are tunable at the top of `engine.py`.

## PPP model

A private tech partner builds and runs this as a **managed reporting service** for
the three agencies, billed per agency per month. The feeds stay on the authority's
own servers and the whole stack is offline-capable (self-contained pages, optional
on-device model) — so there is no cloud lock-in and it degrades gracefully on a
patchy network.
